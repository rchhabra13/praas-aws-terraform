# AI PR Reviewer — praas-agent + AWS Bedrock + Terraform

Automated code review bot: applying the `praas-agent` label to a pull request triggers a review — powered by [praas-agent](https://github.com/IkkaLabs/praas-test/tree/praas-subagents/praas-agent) (IkkaLabs' fork of [the-pr-agent/pr-agent](https://github.com/the-pr-agent/pr-agent)) — generated by AWS Bedrock (Amazon Nova Pro) and posted as a PR comment.

```
label "praas-agent" applied → GitHub Actions → build praas-agent image (base branch only) → assume AWS role (OIDC) → Bedrock (Nova Pro) → review comment posted on PR
```

## Architecture

- **`github/`** — Terraform, `integrations/github` provider. Creates the private GitHub repo.
- **`infra/`** — Terraform, AWS provider. Creates:
  - GitHub OIDC provider + IAM role the Actions workflow assumes (no long-lived AWS keys stored — only the role ARN).
  - IAM policy scoped to `bedrock:InvokeModel` on the Nova Pro model ARN.
- **`vendor/praas-test/`** — git submodule tracking the `praas-subagents` branch of the private [`IkkaLabs/praas-test`](https://github.com/IkkaLabs/praas-test) repo. Contains the actual reviewer (`praas-agent/`, a Python package) and its `Dockerfile.pragent`.
- **`.github/workflows/praas-agent-review.yml`** — triggers when the `praas-agent` label is applied to a PR. Checks out the **base branch** (not the PR head — a PR can't tamper with the reviewer image or the submodule pointer it builds from), assumes the AWS role via OIDC, builds the praas-agent image, and runs it against the PR.

## Prerequisites

- Terraform ≥ 1.6
- AWS account with Bedrock access to Amazon Nova Pro in `us-east-1`
- A GitHub personal access token in the `GITHUB_TOKEN` env var (repo scope) for the Terraform GitHub provider — this same PAT also needs read access to `IkkaLabs/praas-test` (private), since it's reused as the `SUBMODULE_PAT` repo secret for pulling the submodule in CI
- AWS credentials configured locally, for a principal with the permissions in [`infra/deployer-iam-policy.json`](infra/deployer-iam-policy.json) — this is *not* the runtime role the workflow assumes (that one is created by Terraform itself); it's what your own AWS user/role needs to run `terraform apply`. Replace the `<ACCOUNT_ID>`, `<REGION>`, `<STATE_BUCKET_NAME>` placeholders before attaching it.

## Setup (manual — run these yourself)

1. Create the GitHub repo:
   ```bash
   cd github
   terraform init
   terraform apply
   ```
2. Provision AWS infra:
   ```bash
   cd infra
   terraform init
   terraform apply -var="repo_full_name=<owner>/praas-aws-terraform"
   ```
3. Copy the `gha_role_arn` output and add it as a GitHub repo secret named `AWS_ROLE_ARN`.
4. Add a `SUBMODULE_PAT` repo secret — a classic PAT (repo scope) belonging to an account with read access to `IkkaLabs/praas-test`.
5. Push this code to the repo (submodules included: `git push` handles this automatically; a fresh clone elsewhere needs `git clone --recurse-submodules`).
6. Open a PR, apply the `praas-agent` label, and watch the Action post a review.

## Configuration

| Variable / env var | Where | Default |
|---|---|---|
| `region` | `infra` Terraform var | `us-east-1` |
| `bedrock_model_id` | `infra` Terraform var | `amazon.nova-pro-v1:0` |
| `repo_full_name` | `infra` Terraform var | *(required, no default)* |
| `AWS_ROLE_ARN` | GitHub repo secret | set manually from `terraform output gha_role_arn` |
| `SUBMODULE_PAT` | GitHub repo secret | PAT with read access to `IkkaLabs/praas-test` |
| `MODEL` | workflow env | `bedrock/amazon.nova-pro-v1:0` |
| `CUSTOM_MODEL_MAX_TOKENS` | workflow env | `300000` — Nova Pro's context window; required because this model isn't in praas-agent's static token-limit table |

## Cost / cleanup

Bedrock invocations are billable. Tear down with `terraform destroy` in both `infra/` and `github/` when done.

## Design notes

- **praas-agent over the custom script**: the earlier version of this repo hand-rolled a diff-fetch + Bedrock-call + comment-post script. That's been replaced with `praas-agent` (IkkaLabs' fork of the mature, feature-complete `the-pr-agent/pr-agent` project) for a much more capable reviewer — multi-lens review, scoring, many more git-provider/LLM-backend integrations — without maintaining that logic ourselves.
- **Bedrock creds into the container**: praas-agent resolves AWS credentials via Dynaconf-style env vars (`AWS__AWS_ACCESS_KEY_ID`, `AWS__AWS_SECRET_ACCESS_KEY`, `AWS__AWS_SESSION_TOKEN`, `AWS__AWS_REGION_NAME`), fed from the OIDC-assumed role's temporary STS credentials — no static AWS keys anywhere.
- **Base-branch checkout**: same security pattern as `IkkaLabs/praas-test`'s own `pragent-gemini` workflow — build the reviewer image from the PR's base ref, never the head, so a malicious PR can't swap in a different image or submodule commit before it runs with repo secrets and an assumable AWS role.
- IAM policy is scoped to the specific model ARN rather than `bedrock:*` / `resource: "*"`.

## Not implemented

These were considered but intentionally left out of this build to keep the surface area small. Add them later if needed:

- **Terraform remote state backend** — an S3 bucket + DynamoDB lock table for storing `.tfstate` remotely instead of locally. Currently state is local only.
- **CloudWatch Logs write access** — the runtime IAM role does not currently have `logs:CreateLogGroup`/`CreateLogStream`/`PutLogEvents`. GitHub Actions runner logs already cover script output; this would only matter for shipping logs into CloudWatch specifically.
